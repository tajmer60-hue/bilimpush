# Bilim+ — архитектура, схема данных и план развития

## 1. Назначение продукта

Приложение для систематического повторения школьной базы Казахстана (5–11 классы) по основным предметам: математика (алгебра + геометрия), физика, химия, биология, география (включая географию Казахстана), история Казахстана, всемирная история, основы права, информатика. Языки и литература намеренно исключены по требованиям заказчика.

**Ключевой сценарий:** ученик читает теорию по теме → проходит тест → при провале система автоматически формирует **новый** тест, включающий вопросы с прошлыми ошибками и новые вопросы из банка.

## 2. Схема базы данных

```
users            id, name, email (unique), password_hash, is_admin, created_at
subjects         id, title (unique), icon, color, order
sections         id, subject_id → subjects, title, order
topics           id, section_id → sections, title, grade_min, grade_max, theory (HTML), order
questions        id, topic_id → topics, type (single|multiple|truefalse), text,
                 options (JSON), correct (JSON: индекс | [индексы]), difficulty (1–3), explanation
attempts         id, user_id, topic_id, question_ids (JSON), score (0..1), passed,
                 submitted, created_at
answers          id, attempt_id, question_id, selected (JSON), is_correct
progress         id, user_id + topic_id (unique), status (new|read|passed),
                 best_score, attempts_count, updated_at
```

Инварианты:
- `attempt.submitted` — защита от повторной отправки (второй submit → HTTP 400);
- `progress.best_score = max(по всем attempt.score)`;
- `progress.status = passed` ⇔ ∃ attempt с `passed = true`.

## 3. Алгоритм адаптивной генерации теста

```
вход: user, topic, банк вопросов P, размер теста K=10, порог T=0.7
1. нет прошлых попыток →
     выборка K вопросов, сбалансированная по difficulty (1/2/3 по кругу), случайная
2. есть прошлые попытки (обычно после провала) →
     W = все вопросы с is_correct=false по всем прошлым попыткам темы
     L = вопросы последней попытки
     a) взять min(|W|, 0.6·K) вопросов из W (случайный порядок)
     b) добрать новыми: вопросы ∉ seen и ∉ L (случайный порядок)
     c) если банка не хватает — любые ∉ L, затем любые оставшиеся
     d) перемешать
3. отправка → оценка score = correct/K; passed = score ≥ T
4. провал → UI предлагает «Пройти новый тест» (п.2 — W уже содержит новые ошибки)
```

Свойства: ошибки прорабатываются повторно (spacing effect), новые вопросы не дают заучить ответы, вопросы последней попытки не дублируются, пока позволяет банк.

## 4. Безопасность

- Пароли: PBKDF2-HMAC-SHA256, 100 000 итераций, случайная соль (stdlib — без внешних зависимостей).
- Авторизация: JWT (HS256, 30 дней), Bearer-схема; секрет — переменная окружения `BILIM_SECRET`.
- Роли: `is_admin` для контент-эндпоинтов; попытки тестов проверяются на принадлежность пользователю.
- Контент теории рендерится как HTML из доверенного источника (админ-импорт); при добавлении пользовательского контента нужен sanitize.

## 5. Почему такой стек

| Решение | Обоснование |
|---|---|
| FastAPI + SQLAlchemy + SQLite | Быстрый старт, автодокументация Swagger, ноль настроек БД; миграция на PostgreSQL = смена connection string + Alembic |
| Vanilla JS SPA без сборщиков | Работает офлайн и в любом WebView, мгновенно упаковывается в мобильное приложение, нулевой toolchain |
| Контент в JSON + идемпотентный импорт | Контент-мейкеры работают с файлами, не трогая код; версионирование через git |

## 6. Мобильная версия (следующий этап)

SPA спроектировано как основа мобильной обёртки — **логика и контент переиспользуются на 100%**:

```bash
npm init -y && npm i @capacitor/core @capacitor/cli @capacitor/android
npx cap init "Bilim+" kz.bilim.app --web-dir=frontend
npx cap add android
# в capacitor.config.json: server.url = "https://<ваш-сервер>" (или офлайн-бандл + локальная БД)
npx cap sync && npx cap open android   # → сборка APK в Android Studio
```

Варианты поставки контента в мобильную версию:
1. **Онлайн:** приложение указывает на сервер API (минимум изменений — уже готово).
2. **Офлайн:** включить PWA (service worker кэширует frontend), а API — поднять локально (termux-вариант не рекомендуется; лучше синк контента).
3. **Гибрид:** теория кэшируется, тесты и прогресс — через API.

Дальнейшие шаги мобилизации: push-уведомления («повтори слабую тему»), виджет прогресса, тёмная тема.

## 7. Масштабирование контента

Стартовый банк: 46 тем / 462 вопроса. План покрытия программы 5–11 классов — ≈300 тем. Процесс:
1. Темы-заглушки создаются через `POST /api/admin/topics` (theory пустая — тема скрыта от выдачи, пока questions_count=0: тест не соберётся, API вернёт 400 «банк пуст»).
2. Вопросы добавляются пачками через JSON-импорт.
3. Рекомендация по качеству: ≥12 вопросов на тему (чтобы ретесты не повторялись), баланс difficulty 40/40/20, у каждого вопроса — explanation.

## 8. Что добавить следующим (бэклог)

- **ЕНТ-режим:** смешанные тесты (математическая грамотность + предмет), таймер 3–4 часа, percentile-оценка, история баллов по датам.
- **Spaced repetition:** повторение пройденных тем по кривой забывания (1/3/7/14 дней).
- **Геймификация:** стрики, бейджи, рейтинг классов.
- **Учительский кабинет:** классы, назначение тем, аналитика по ученикам.
- **i18n:** казахский интерфейс/контент (структура JSON уже готова — добавить поле `lang` или дубль файлов `*_kk.json`).
- **Деплой:** Dockerfile (backend+frontend одним образом), CI, бэкапы SQLite → миграция на Postgres.
